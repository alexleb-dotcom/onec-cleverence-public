# Validation engine

The validation engine is registry-driven and fail-closed.

## Proof model

```text
task + actual source / deployed baseline
→ requirements contract from RULES/rule_registry.json
→ requirements gate
→ technical review plan from the same registry
→ evidence ledger
→ implementation + deterministic checks
→ evidence-bounded gap discovery
→ independent semantic/reverse review
→ release gate
→ runtime acceptance
```

A clean analyzer is not coverage. A written rule is not enforcement. A `PASS` without evidence is invalid. A technically complete plan cannot compensate for a blocking OPEN business contract.



## Proof-claim integrity

Read `KNOWLEDGE/PROOF_CLAIM_INTEGRITY.md`. The validation engine distinguishes execution from narration: skill-shaped prose, a self-authored checklist or an `N/N` count is not evidence that the registry/gates ran. Any readiness/compliance claim must be bounded by the actual current plan/ledger/gate state. Evidence is property-specific; an analog cannot be silently promoted from “this construction exists” to proof of business semantics, performance or runtime behavior. A newly discovered parser/runtime/user-review defect invalidates dependent prior proof until the affected closure is revalidated.

## Requirements proof

Before non-trivial technical design, `TOOLS/build_requirements_contract.py` creates an intentionally unresolved functional-contract ledger and `TOOLS/requirements_gate.py` adjudicates it. Requirements rules live in the same `RULES/rule_registry.json` as technical rules.

Depth scales by risk rather than by a fixed questionnaire. Available evidence is mined first; only unresolved behavior/scope/ownership/acceptance gaps should become user questions. `REQUIREMENTS_BLOCKED` forbids production-ready technical design. The gate recomputes the risk-required functional fields and rule/check set from the registry: deleting an unresolved row, duplicating an ID or supplying a weaker partial ledger cannot convert UNKNOWN into READY. The exact supplied task text remains hash-bound in the contract, but a later user instruction is knowable only after it is supplied again; any material task change therefore rebuilds the contract and downstream plan. The core functional spine cannot be marked `NOT_APPLICABLE`, and a narrower requirements surface/risk cannot authorize a wider technical plan. When a recorded requirements source remains accessible, the gate rehashes its current bytes and blocks stale contracts after source drift.

## Rule lifecycle

Every reusable rule must answer:

1. **Activation** — what source/context signal routes it?
2. **Checks** — what exact questions must be adjudicated?
3. **Evidence** — machine/source/semantic/runtime proof required for PASS?
4. **Regression** — how do we test activation and enforcement?
5. **Release** — what unresolved status blocks or downgrades delivery?

`RULES/rule_registry.json` is the only executable source of truth. Generated profile/semantic views must not be edited independently.

## Tier model

Tier 0 rules always require a disposition. They may be `NOT_APPLICABLE` only with a reason and only when the review plan does not require the corresponding gate. A plan gate routed as `REQUIRED` cannot be bypassed by relabeling its ledger row `NOT_APPLICABLE`. Tier 1 rules are routed from mechanisms/project context. Tier 2 references are loaded only as evidence.

## Bidirectional review

`CODE_TO_STANDARDS` starts from changed constructions and asks which rules/contracts apply.

`STANDARDS_TO_CODE` starts independently from every routed registry rule/check and asks where the evidence exists in code/source/runtime.

The second pass must never be generated by copying findings from the first. The validation-ledger builder seeds both passes unresolved, and the release gate requires a resolved `CODE_TO_STANDARDS` construction pass plus an independent `STANDARDS_TO_CODE` row for every routed registry rule with its exact registered checks. Empty reverse sections are blocking, even when every local rule says PASS. Reverse disposition must also agree with the owner rule: a PASS rule cannot be hidden behind `STANDARDS_TO_CODE = NOT_APPLICABLE`.

## Affected-closure reopen

A validation failure invalidates only the closure and evidence dependencies it actually contradicts. Do not restart unrelated discovery or discard independently valid proof by default.

After a material fix, reroute and re-evaluate every dependent obligation/fingerprint whose input identity or assumption changed. Unaffected closures stay closed only when their declared dependencies still match. A broad restart is justified only when the failure invalidates a shared upstream dependency.

## Evidence-bounded discovery

Known-rule coverage and external standards search do not by themselves expose cross-rule or whole-change-set omissions. `KNOWLEDGE/GAP_DISCOVERY_PROTOCOL.md` therefore defines independent risk lenses and a structured hypothesis lifecycle.

Discovery is not free-form brainstorming. Every hypothesis needs exact source anchors, one falsifiable statement, a concrete counterexample and a falsifier. It can widen review or request evidence, but cannot establish a defect, PASS or universal rule without independent evidence. `TOOLS/release_gate.py` validates every lens and hypothesis disposition.

For multi-BSL change-sets, `TOOLS/analyze_changeset_architecture.py` supplies conservative REVIEW candidates. Its zero-result is not semantic evidence; cross-object responsibility/owner mapping remains mandatory.

## Adversarial proof

`adversarial_case_contract` in the registry makes negative-path review executable without turning it into an unbounded checklist. From R1 upward, a PASS `ADVERSARIAL_VALIDATION` gate requires at least one structured `adversarial_cases` counterexample with explicit status and concrete evidence. Pending runtime/profiling cases downgrade readiness; unresolved/blocking cases block. The old `architecture_platform` ledger collection is not part of new skeletons because L1-L6 `review_levels` already own that proof and duplicate structures invite drift.

## Evidence

Evidence should be concrete and dependency-bound: source path/hash, declaration/call site, standard URL/revision, analyzer report, runtime scenario/result, benchmark, metadata contract, active Cleverence Business Process, etc. A PASS evidence item has at least `{kind, ref}`. MACHINE evidence additionally names a registered machine report; RUNTIME evidence names a runtime case whose own status is PASS. A free-form string or an unlinked report reference is not proof.

Proof row IDs are unique. Duplicate gate/rule/check/review/report/runtime IDs are invalid instead of being silently collapsed. Reusing evidence is allowed only while all declared dependencies remain unchanged. Each reusable dependency is `{kind, id, fingerprint}`; candidate/baseline/project-context/requirements fingerprints are checked against the current plan, and `changed_dependencies` invalidates reuse by dependency identity `(kind,id)` rather than by exact old/new object equality.

## Release outcomes

`TOOLS/release_gate.py` is the final decision point:

- `BLOCKED`: unresolved/blocking evidence; do not say ready.
- `READY_FOR_RUNTIME_TEST`: static/semantic proof allows a test build but runtime/profiling remains pending.
- `PROVEN`: all required evidence is complete.
- `ANALYSIS_COMPLETE`: analysis-only task is fully covered.

The release gate checks registry identity, exact plan/ledger routing and project context, candidate hashes, SHA-bound baseline identity, accessible current candidate/baseline/project-context/requirements bytes, gates, Tier-0/routed rule coverage, child checks, independent bidirectional standards rows, discovery lenses/hypotheses, evidence/report/runtime links, evidence reuse dependencies, L1-L6 review levels, duplicate IDs, blocking findings and unsupported PASS/NOT_APPLICABLE claims. A source-bearing 1C/Cleverence plan cannot omit the forward `CODE_TO_STANDARDS` pass. MACHINE evidence cannot prove PASS through a named report whose own `result` is not PASS.


## Implementation reachability proof

A new routine is not validated by local correctness alone. The implementation pass must prove a live integration path from the intended runtime entrypoint to every new/changed helper that is supposed to alter behavior. Use candidate + baseline call-graph evidence. `Export` is API visibility, not invocation evidence. Platform/dynamic dispatch that cannot be statically resolved stays evidence-pending and needs an exact callback/event contract and runtime case.

The release gate therefore requires an explicit disposition for `IMPLEMENTATION_REACHABILITY`; a defined-but-unreachable helper or orphan new subgraph is a blocking implementation defect.

## Artifact scope discovery

`SOURCE_FIRST` begins with factual inventory of the supplied corpus, not assumptions derived from filenames. Mixed archives must be classified before relevance filtering so supporting documents/forms/modules/schemas are not silently excluded.
